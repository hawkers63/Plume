French–English Conversation Translator
======================================

Project purpose
---------------

Build a small Windows 11 desktop application that translates conversational
French and English in either direction. Its central purpose is not merely to
produce one literal translation: it should give the user a useful choice of
natural alternatives for an ongoing conversation.

For every submitted phrase, the application should:

1. Identify whether the source is English or French.
2. Translate it into the other language, keeping its meaning, register,
   punctuation, and emotional tone as closely as the languages permit.
3. Produce five genuinely distinct, natural variations in the target language.
4. Display each variation followed by its English equivalent in brackets.
   This makes the proposed French phrasing easy for an English-speaking user
   to understand before copying it into a conversation.
5. Allow the user to copy either the main translation or an individual
   variation quickly.

The application should be called Translator (the final product name can be
changed later). It should follow Scriptorium’s practical style: a dark,
native-feeling CustomTkinter interface; clear British English labels and error
messages; explicit privacy information; no silent rewriting; and an optional
cloud or local model backend.


Required behaviour
------------------

Language direction
~~~~~~~~~~~~~~~~~~

The default mode is Auto-detect. The application determines whether the input
is English or French and sets the target to the other language:

    English input -> French translation
    French input  -> English translation

Provide manual direction controls as well:

    Auto-detect | English -> French | French -> English

Manual selection is important for very short or ambiguous input such as
“non”, “merci”, names, quotations, mixed-language messages, or regional
expressions. The model should report an uncertainty warning rather than
pretend an ambiguous input has been identified with certainty.

The source language, target language, and the reason for an uncertainty should
be returned in the response data and shown in the interface. Never infer a
different meaning just to make the translation sound smoother.

Main translation
~~~~~~~~~~~~~~~~

The main translation is the closest natural rendering of the user’s sentence.
It must preserve:

- the original intent and level of certainty;
- register: casual, warm, professional, terse, playful, etc.;
- emotion and conversational rhythm where possible;
- directness, politeness, hedging, slang, and ellipses when they are material;
- proper names, numbers, dates, URLs, handles, code, quoted content and
  placeholders unchanged unless the user explicitly asks for a translated
  explanation of them.

The translator must not add facts, commitments, flirtation, sarcasm, offence,
or extra context. It should say when a direct one-to-one rendering is
impossible or when a phrase has a culturally meaningful alternative.

Five variations
~~~~~~~~~~~~~~~

Produce exactly five alternative target-language phrasings. They should retain
the source’s style—not be arbitrary changes in formality or emotion. Each must
be natural in the target language and retain the same basic meaning.

The UI presentation depends on direction:

    English source:
      Source: It’s good to see you, what’s been happening?
      Main French: Ça fait plaisir de te voir, qu’est-ce qui s’est passé ?
      1. Je suis content(e) de te voir, quoi de neuf ?
         [I’m pleased to see you; what’s new?]
      ... through 5

    French source:
      Source: Salut... c’est calme ce soir. !
      Main English: Hi… it’s quiet tonight!
      1. Hey… it’s pretty quiet this evening!
         [Hey… it’s pretty quiet this evening!]
      ... through 5

For French-source input, the bracketed English text will usually match the
visible variation, but it still has value as an explicit confirmation and
keeps the output layout consistent. For English-source input, the bracket is a
plain-English gloss of the French variation, not a word-for-word back-
translation. The document and implementation should call this a “meaning
check”, so users do not mistake it for a literal linguistic equivalence.

Variation quality rules:

- The main translation must not be repeated among the five alternatives.
- Alternatives must be meaningfully different (word choice, idiom, word
  order, or natural conversational phrasing) rather than punctuation-only
  variants.
- The alternatives must not change pronoun choice from informal “tu” to
  formal “vous”, or vice versa, unless the source offers no basis for a choice.
  If that choice is genuinely unclear, preserve a configured default and show
  a small warning or let the user choose a formality setting.
- Gender-dependent French wording should be avoided where possible. When it
  cannot be avoided, use a neutral phrasing, offer an appropriate form such as
  “content(e)”, or label the decision clearly rather than guessing the user’s
  gender.
- Do not manufacture regional slang. A future regional setting can explicitly
  support France, Belgium, Quebec, or a neutral international French option.

Conversation workflow
~~~~~~~~~~~~~~~~~~~~~

The first release should optimise for fast, real-time chat assistance:

- Ctrl+Enter translates the current input.
- Ctrl+V / Paste places clipboard text in the input area.
- Every output row has its own Copy button.
- “Copy main translation” is the most prominent copy action.
- Clear starts the next message without deleting any saved settings.
- The user can reverse the direction before translating if auto-detection gets
  it wrong.
- A compact history of recent requests is optional for a later release. Do not
  store it in version 1 unless the user consciously enables local history.


Recommended technology and compatibility with Scriptorium
----------------------------------------------------------

Use the same toolset and engineering approach as C:\Scriptorium:

- Python 3.10 or later.
- CustomTkinter for the UI, with Tkinter’s `messagebox`, `filedialog`, and
  `Text` widget when their native features are useful.
- `urllib.request` and `urllib.error` from the Python standard library for
  HTTP. Do not add `requests`, an Anthropic SDK, or another HTTP dependency.
- `json`, `threading`, `re`, `os`, `sys`, and other standard-library modules
  for configuration, response parsing, background work and validation.
- Claude API as the cloud backend, using the Messages endpoint. The API key is
  stored in the local config or read from `ANTHROPIC_API_KEY`.
- Ollama as the privacy-first local backend, using `/api/chat` and `/api/tags`
  on `http://localhost:11434`.
- PyInstaller for the optional single-file Windows executable.

The only required package should remain:

    customtkinter>=5.2.0

No document import/export is necessary for the first translation-focused
release. It can be added later if there is a real need. Keeping version 1
single-purpose will make it faster and safer for live chat use.


Proposed project layout
-----------------------

Create the following initial layout in C:\Translator:

    C:\Translator\
        translator.py
        requirements.txt
        translator_config.example.json
        translator.spec
        Translator.bat
        README.md
        project.txt
        icon\
            icon-96.ico
            icon-96.png
        tests\
            test_translator_logic.py

`translator.py` should initially be one well-organised module, like
Scriptorium. Avoid premature package splitting. Structure it with clear,
separable sections in this order:

1. Application constants and configuration paths.
2. Defaults and load/save configuration functions.
3. Input protection and small deterministic validation helpers.
4. Prompt construction and structured-result parsing.
5. Claude and Ollama backend functions.
6. Settings dialogue.
7. Main CustomTkinter application and UI callbacks.
8. `main()` entry point.

When the application grows, the deterministic functions can be moved into a
separate module only after tests establish their behaviour.


Configuration design
--------------------

Use `translator_config.json`, generated from defaults on first save. As with
Scriptorium, do not commit the live file because an API key may be stored in
it. When frozen with PyInstaller, use `%LOCALAPPDATA%\Translator` rather than
the temporary executable location.

Recommended example configuration:

    {
      "backend": "anthropic",
      "anthropic_api_key": "",
      "anthropic_model": "claude-sonnet-4-6",
      "ollama_model": "llama3.1:8b",
      "privacy_ack": false,
      "default_direction": "Auto-detect",
      "default_french_formality": "Informal (tu)",
      "default_french_variant": "Neutral international French",
      "protect_placeholders": true,
      "save_local_history": false
    }

The configuration writer should use the same atomic-save pattern as
Scriptorium: write a temporary sibling JSON file, flush it, then replace the
old file. If an existing configuration file is malformed, do not silently
overwrite it from an automatic save. The Settings window may offer an explicit
recovery save after informing the user.

Security and privacy requirements:

- Explain on first use of Claude that submitted text goes to Anthropic.
- Explain that Ollama keeps processing on the local machine, subject to the
  user’s own Ollama configuration.
- Store the API key only in the config file if the user deliberately enters
  it; otherwise prefer `ANTHROPIC_API_KEY`.
- Display a masked key in Settings.
- Do not log source messages, translated messages, headers or API keys.
- Do not save history by default.


Structured response contract
----------------------------

Translation is too important to parse as informal prose. Require each backend
to return one JSON object and validate it before rendering anything in the UI.
Use this contract:

    {
      "source_language": "English",
      "target_language": "French",
      "language_confidence": "high",
      "language_note": "",
      "main_translation": "...",
      "variations": [
        {
          "translation": "...",
          "english_meaning_check": "..."
        }
      ],
      "notes": ["..."]
    }

Validation must enforce all of the following before result display:

- `source_language` and `target_language` are allowed values and are opposite.
- When direction was manually selected, the target matches the selection.
- `main_translation` is a non-empty string.
- `variations` is a list of exactly five objects.
- Every variation includes two non-empty strings.
- Normalised variations are not duplicates of each other or the main
  translation. Normalisation should case-fold, collapse whitespace, and ignore
  superficial terminal punctuation only; do not use it to alter the text shown
  to the user.
- A malformed model response, extra prose, null value, missing field, or
  incorrect number of variants produces a clear retryable error. Do not
  partially display an unreliable result.
- `language_note` and `notes` are optional but must be converted into safe,
  short strings/lists before the UI uses them.

For placeholder protection, reuse Scriptorium’s approach. Replace protected
material with tokens such as `⟦PH0⟧` before sending the request, make the prompt
require the tokens to be returned exactly, then restore and verify them in the
validated result. Protect bracketed placeholders, template markers, URLs, file
paths, e-mail addresses, @handles, dates/numbers as appropriate. The first
implementation must at least preserve tokens it recognises; it must never
claim it can perfectly identify every name or idiom.


Prompt design
-------------

The backend prompt is central to quality. It should be produced by a pure
function such as:

    build_translation_prompt(direction, french_formality, french_variant,
                             protect_tokens)

Its instructions should be explicit and testable in spirit:

    You are a precise conversational translator between English and French.
    Determine the source language unless the application supplies a forced
    direction. Translate faithfully and naturally into the other language.
    Preserve meaning, emotional tone, register, punctuation and intent.
    Do not add facts, soften or intensify commitments, invent context, or
    explain the translation inside the translated text.

    Return one primary translation and exactly five distinct, idiomatic
    alternatives in the target language. Keep each alternative within the
    source tone and formality. Each alternative must include a concise English
    meaning check. Do not repeat the primary translation.

    Respect the selected French address form and regional preference. When
    formality, gender or language detection is genuinely uncertain, choose the
    least presumptive natural wording and record one short note.

    Return only the required valid JSON object—no Markdown fences or prose.

For user text, send a small explicitly labelled envelope rather than mixing
instructions with the phrase. For example:

    Requested direction: Auto-detect
    French address preference: Informal (tu)
    French variant: Neutral international French
    Text to translate:
    <the masked user text>

Do not attempt to use a general translation prompt that merely says “translate
this”. The requested five meaningful alternatives, formality consistency,
English meaning checks, and JSON-only contract are all necessary constraints.


User interface concept
----------------------

Follow Scriptorium’s dark two-pane feel, but make the translation task faster
and more legible than a revision/diff workflow.

Window
~~~~~~

- Title: `Translator — French ↔ English conversation helper`.
- Initial size: approximately 1180 × 760 pixels; minimum 920 × 600.
- Dark CustomTkinter appearance and blue theme, matching Scriptorium.
- User-facing wording, help text, and errors in British English.

Toolbar
~~~~~~~

- Direction segmented control: Auto-detect, English -> French,
  French -> English.
- French address control: Informal (tu), Formal (vous), Let Translator decide.
  It is enabled when French is the target or can remain available and clearly
  labelled for the next translation.
- French variant control: Neutral international French initially; regional
  choices can be added after testing.
- Settings button.

Main content
~~~~~~~~~~~~

Use two columns of equal width.

Left column: “Message to translate”

- An editable, word-wrapped CustomTkinter textbox.
- Character count below it.
- Paste, Clear, and Translate buttons.
- A short hint: “Ctrl+Enter to translate”.

Right column: “Translation”

- A read-only primary-translation card at the top, with a large Copy button.
- A small language label, for example `English → French · detected with high
  confidence`.
- A “Five natural alternatives” section below, containing five individually
  bordered cards. Each has its French/English output, a muted bracketed meaning
  check, and a Copy button.
- An advisory strip, hidden until needed, for uncertainty and preservation
  warnings. It should say what is uncertain, not lecture the user.

Actions and lifecycle
~~~~~~~~~~~~~~~~~~~~~

- `Translate` starts a worker thread and changes to `Translating…` while
  disabled.
- Capture an incrementing request ID. Ignore a result if a later request,
  Clear action, or window close has superseded it. This is the same important
  stale-callback protection already used in Scriptorium.
- Snapshot settings and input at request start. Settings changes apply to the
  next request, not a request already in flight.
- If input changes while a request is underway, render the result only with a
  prominent `Generated for an earlier message` advisory. Do not overwrite the
  source text.
- Copy actions operate only on validated visible results.
- Result cards must be cleared when the user explicitly clears the conversation
  or starts a clearly new input, but do not erase them automatically on every
  keystroke; that would make comparison inconvenient.

Status bar
~~~~~~~~~~

Match Scriptorium’s transparent status handling, for example:

    Backend: Claude · claude-sonnet-4-6 — text is sent to Anthropic | 47 characters

or:

    Backend: Ollama · llama3.1:8b (local) — stays on this machine | ready

Never include the actual submitted phrase in the status line, window title, or
an error message, as these may be visible in screenshots or logs.


Backend implementation notes
----------------------------

Reuse and adapt Scriptorium’s established backend patterns rather than copying
them without review:

- `BackendError` for friendly recoverable network, HTTP and parsing failures.
- `call_anthropic()` sends JSON to `https://api.anthropic.com/v1/messages` with
  `x-api-key`, `anthropic-version`, and `content-type` headers; request a
  sufficient `max_tokens` budget for one translation plus five alternatives.
- `call_ollama()` sends `stream: false`, `format: "json"`, and system/user
  messages to `/api/chat`.
- `list_ollama_models()` obtains local model names from `/api/tags` for the
  Settings dialogue’s Detect button.
- `run_backend()` selects the configured backend from a copied configuration
  snapshot.

The response parser should tolerate an accidental Markdown code fence only if
the JSON inside it is valid. It must not accept random prose plus a fragment of
JSON as an apparently successful translation without validating the full data
contract above. Error text should invite the user to retry, shorten a large
message, or select a different backend where relevant.

Important limitation: local models vary substantially in French translation
quality and reliable JSON compliance. Treat Ollama as a supported private
option, but recommend a capable multilingual model and make validation strict.
If the local result fails validation, show a retryable failure rather than
displaying fewer than five options or made-up fields.


Build sequence
--------------

Phase 1 — Create the small application skeleton
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. Create the project files listed above and copy only the generic patterns
   from Scriptorium: configuration location, atomic JSON saving, CustomTkinter
   setup, settings dialogue shell, background-worker lifecycle, and packaging
   specification.
2. Set `APP_NAME = "Translator"`, create `DEFAULT_CONFIG`, and implement
   `load_config()` / `save_config()` with malformed-config protection.
3. Build the static UI with all expected controls, empty result cards, status
   bar, keyboard shortcut, copy buttons, and an operational Clear button.
4. Manually run it before connecting any backend. Check window resizing,
   keyboard focus, tab order, text wrapping, disabled state, dark-theme
   contrast, and clipboard behaviour.

Phase 2 — Implement deterministic translation logic
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. Implement `normalise_for_uniqueness()`, placeholder masking/restoration,
   source-size validation, and the strict `parse_translation_result()`.
2. Write unit tests first for normalisation, malformed JSON, missing fields,
   duplicate variants, five-variation enforcement, placeholder round trips,
   and forced-direction validation.
3. Implement `build_translation_prompt()` as a pure function. Test its key
   constraints by asserting that it mentions the selected direction,
   formality, placeholder token policy, exactly five variants, and JSON-only
   output.

Phase 3 — Connect the backends
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. Adapt Scriptorium’s Claude `urllib` call for the new prompt and structured
   result contract.
2. Adapt the Ollama call, retaining `stream: false` and JSON mode.
3. Build the Settings dialogue: backend switch, masked Claude key entry,
   model choice, Ollama model field, Detect button, formality and privacy
   controls as appropriate.
4. Add the initial cloud privacy notice and clear errors for missing keys,
   unavailable Ollama, HTTP failures, timeouts and invalid model output.

Phase 4 — Integrate and polish the interaction
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. Connect Translate to the worker thread. Use request IDs to reject stale
   callback results.
2. Render only validated results. Place main translation and variations in
   separate copyable cards.
3. Add detection confidence and short, actionable notes without burying the
   output.
4. Add lightweight input length limits appropriate to the selected model and
   report them before a costly request. A sensible initial limit is 2,000
   characters; make it configurable later if needed.
5. Validate the interactive experience with the bilingual test set below.

Phase 5 — Package and document
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. Write the README: prerequisites, installation, run command, backends,
   privacy, config, troubleshooting, and version-1 limitations.
2. Create `Translator.bat` for convenient source launching.
3. Adapt `translator.spec` from Scriptorium and include the CustomTkinter
   assets and chosen icon.
4. Build with PyInstaller and test the executable on a Windows user profile.
   Confirm configuration writes to `%LOCALAPPDATA%\Translator`, not the
   extracted executable folder.


Test and acceptance plan
------------------------

Automated unit tests
~~~~~~~~~~~~~~~~~~~~

At minimum, `tests\test_translator_logic.py` should cover:

- valid English → French and French → English result objects;
- every malformed response class: invalid JSON, scalar JSON, no primary,
  empty primary, non-list variations, fewer/more than five, bad variation
  objects, empty translation, empty meaning check;
- duplicate alternatives after harmless normalisation;
- primary translation duplicated as an alternative;
- manual direction mismatch;
- malformed configuration does not get overwritten by automatic save;
- placeholder tokens are restored and each missing/changed token creates a
  warning;
- no source content is exposed by normal status/error formatting;
- the stale-request test: a later request cannot have its UI result replaced
  by an earlier response.

Translation quality test set
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Run representative manual tests against both available backends and record
results. Include:

- Casual English: `It’s good to see you, what’s been happening?`
- Casual French with expressive punctuation: `Salut... c’est calme ce soir. !`
- Informal/formal contrast: `Could you send it to me tomorrow, please?`
- Ambiguous address: `You were right.`
- Gender-sensitive phrase: `I’m really pleased to meet you.`
- Idiom: `I’m just pulling your leg.`
- Message containing `[Name]`, `{amount}`, a URL and a date.
- Mixed-language input: `Merci for helping with the booking.`
- Very short ambiguity: `non`, `OK`, `allô`, and a proper name.
- A sensitive or emotionally tense sentence, ensuring no escalation or added
  sentiment.

For every test, assess semantic fidelity, tone preservation, natural target
language, exactly five non-duplicate alternatives, correct bracketed English
meaning checks, intact protected tokens, and appropriate uncertainty notes.

Manual UI checks
~~~~~~~~~~~~~~~~

- Ctrl+Enter works from the input textbox and does not insert an unintended
  newline.
- Buttons disable/re-enable correctly across successful, failed and cancelled
  requests.
- Close during a request produces no Tk callback exception.
- Copy buttons place exactly the expected item on the clipboard.
- Auto-detection can be overridden reliably.
- Small windows remain usable and long output wraps instead of disappearing.
- Dark-mode text retains sufficient contrast.
- No API key or user phrase appears in console diagnostics beyond intentional,
  local developer logging (which should be off by default).


Decisions deliberately deferred from version 1
-----------------------------------------------

- Speech recognition and spoken output. These introduce microphone, consent,
  latency and language-voice choices. Build them only after the typed workflow
  is dependable.
- Automatic sending to WhatsApp, Messenger, Discord or other services. Copying
  is safer and avoids account permissions and accidental messages.
- Persistent conversation history or cloud synchronisation. Privacy and clear
  consent need deliberate product decisions first.
- Additional language pairs. The data contract and UI can support them later,
  but French ↔ English quality and formality handling should be calibrated
  first.
- Dictionary-style word-by-word analysis. It is a separate experience from
  fast conversational translation and should not complicate the first screen.
- Regional French presets beyond neutral international French. Add only after
  native-speaker review and tests demonstrate real value.


Definition of done for the first usable version
------------------------------------------------

The first version is ready when it is a small, dependable desktop program that
can accept an English or French chat message; use auto or forced direction;
return one faithful main translation and exactly five validated, natural
same-tone alternatives; show the English meaning check beside every
alternative; preserve configured French formality and recognised placeholders;
copy individual results; make the cloud/local privacy distinction clear; and
handle bad networks, malformed responses and late background callbacks without
crashing or showing misleading partial output.

Build this incrementally, validating the deterministic data contract before
judging translation fluency. For a conversation helper, dependable output
shape, clear context choices and easy copying matter just as much as the model
itself.
