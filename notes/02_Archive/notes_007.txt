0. What this note is and is not
------------------------------------------------------------------------
Live plume.py was re-read in full before writing this note, alongside
ROADMAP.md and notes_001 through notes_006 (001-003 archived, 004-006
now landed). Confirmed already shipped: finishing-touch picker (notes_004),

local history with favourites (v1.4-v1.5, not covered by any existing note).
Confirmed NOT yet landed: only Voice/TTS (roadmap v1.6) remains scheduled.

This note does not repeat any bug or feature already on file. It proposes:
  1. A small refactor: the toolbar's top row has needed manual column
     renumbering on every one of the last three releases (v1.3, v1.4, v1.5)
     as new controls were inserted. The next addition will hit the same tax.
  2. Feature: local history entries do not record which "Situation" (v1.4)
     was used, so a favourited entry loses that context permanently.
  3. Feature: history entries can be copied but not reopened into the
     working translator, so revisiting a good past phrasing to tweak it
     means retyping the source text and re-spending an API call.

------------------------------------------------------------------------
1. Refactor -- stop hand-counting toolbar columns
------------------------------------------------------------------------
Rationale, grounded in the actual edit history:

  PlumeApp._build_toolbar (plume.py, from approximately line 1571) lays
  out its top row with `ctk.CTkLabel(...).grid(row=0, column=N, ...)` at
  fixed literal column numbers, plus a single spacer column that must sit
  just before the right-pinned buttons.

  Tracing the git history of just this one row: v1.3 added Backend at
  columns 2-3 and moved the spacer from column 2 to 4; v1.4 inserted Swap
  at column 2, pushing Backend to 3-4 and the spacer to 5; v1.5 inserted
  History at column 6, pushing Settings from 6 to 7. Three releases in a
  row, the same block needed every literal column number after the
  insertion point re-counted by hand. Voice (v1.6) is likely to add at
  least one more toolbar control (a mute toggle, or a "Speak" button
  the roadmap does not rule out living on the toolbar), which would make
  a fourth manual renumbering.

  This is refactoring only: identical visual output, no behaviour change,
  no new dependencies.

------------------------------------------------------------------------
2. Feature -- record the situation on each history entry
------------------------------------------------------------------------
Rationale, grounded in the current code:

  translate() (plume.py, approximately line 933) already accepts a
  *situation* parameter and threads it into the envelope via
  build_user_envelope(). PlumeApp._translate captures it as a local
  `situation` variable (approximately line 1957) and passes it into
  worker()'s call to translate(). But make_history_entry() (approximately
  line 371) and PlumeApp._save_to_history (approximately line 2107) only
  ever see `source_text` and the parsed `result` -- `situation` is not
  threaded through to either.

  Result: translate "See you tomorrow" with situation "formal work email
  to my boss", favourite the entry so it survives Clear history -- and six
  months later the History window shows only the source and translation,
  with no record of *why* that particular register was chosen. The one
  piece of context that most explains an unusual phrasing choice is
  exactly the piece not kept.

------------------------------------------------------------------------
3. Feature -- reopen a history entry into the working translator
------------------------------------------------------------------------
Rationale, grounded in the current code:

  HistoryDialog._build_entry_card (plume.py, approximately line 1428)
  offers Favourite, Copy and Delete per entry. Copy only places the main
  translation on the clipboard; there is no way to bring a past source
  phrase and its five alternatives back into the main window to compare,
  adopt an alternative with "Use this", or add a finishing touch.

  PlumeApp._render_result (approximately line 2100) already accepts any
  dict with "main_translation" and "variations" keys and asks nothing
  else of it -- and make_history_entry() was built with exactly those key
  names. A history entry can therefore be handed to _render_result
  directly, with no network request and no change to _render_result
  itself.

------------------------------------------------------------------------
4. User-visible behaviour
------------------------------------------------------------------------
Refactor (1): none. Pixel-identical output; existing tests and manual
behaviour are unaffected.

Feature (2):
  1. When a translation is saved to local history and a situation was
     given, the History card shows a third, italicised line: "Situation:
     <text>", beneath the source and translation. No line is shown when
     no situation was given, matching how the envelope already omits an
     empty Situation line.
  2. No new Settings field, no new consent prompt -- this rides on the
     existing "Save translations to local history" opt-in.

Feature (3):
  1. Each history card gains a "Reopen" button in its button column.
  2. Clicking it: replaces the main window's input box with the entry's
     source_text; replaces the Situation box with the entry's situation
     (blank if none); renders the entry's main_translation and five
     variations exactly as a fresh result would render, with "Use this",
     Copy and the finishing-touch picker all working normally; then
     closes the History window so the user lands back on the translator.
  3. No network request is made and the model is not re-contacted.
  4. A subsequent Translate on the reopened text behaves exactly as any
     other translation (including saving a new history entry, if enabled).

6.3 Feature 3 -- reopen a history entry

New method on PlumeApp, immediately after _use_as_main (approximately
line 1900), reusing the exact "master" access pattern already used by
SettingsDialog._save to reach back into the main window:

    def _reopen_history_entry(self, entry):
        """Load a saved history entry back into the working translator.

        No network request is made; _render_result already accepts any
        dict with "main_translation" and "variations", which is exactly
        the shape make_history_entry() produces.
        """
        self.input_box.delete("1.0", "end")
        self.input_box.insert("1.0", entry.get("source_text", ""))
        self.situation_entry.delete(0, "end")
        self.situation_entry.insert(0, entry.get("situation", ""))
        self._on_input_change()
        self.advisory.grid_remove()
        self.finishing_touch_var.set(FINISHING_TOUCH_NONE)
        self._render_result(entry)

8. Risks
------------------------------------------------------------------------
  - Reopen and language_confidence. A reopened entry's language label
    reads "detected with low confidence" regardless of what was actually
    detected, because format_language_label() defaults an absent
    "language_confidence" key to "low" and history entries do not store
    it. Cosmetic only -- the translation and variations themselves are
    exact -- but worth a one-line mention if this lands, since a user
    could otherwise read "low confidence" as a fresh (and wrong) signal
    about a translation they already trusted enough to favourite. Storing
    "language_confidence" alongside "situation" in make_history_entry()
    would remove this entirely and is a trivial addition if desired.
  - Existing history entries lack "situation". Handled via `.get(...,
    "")`, matching how config_data's own optional fields are already
    read defensively elsewhere in this file.
  - The toolbar refactor changes literal column numbers to a running
    counter; a careless edit could still insert a widget without
    incrementing `col`, silently overlapping two controls in one cell.
    This is a strictly smaller risk surface than today (one counter to
    keep in step, instead of every subsequent literal needing re-counting
    by hand), not a new one.

9. Deliberately not proposed
------------------------------------------------------------------------
  - Voice / TTS (roadmap v1.6): out of scope for an ideation pass whose
    brief is targeted, incremental refinements; TTS is a substantial
    enough addition to warrant its own dedicated note when picked up.
  - Applying the same column-counter treatment to the toolbar's bottom
    row (French form / Me / You) or to SettingsDialog's single-column
    layout: neither has needed renumbering yet, so refactoring them now
    would be pre-emptive rather than grounded in an observed pain point.
  - A "recent situations" dropdown on the Situation box: a reasonable
    follow-on once real usage shows which phrasings get reused, but not
    grounded in anything observable in the code today, unlike the three
    items above.
  - Reopening into a *new* history entry on the next Translate: already
    covered for free, since a reopened entry's Translate click runs the
    normal _translate() path unchanged.
