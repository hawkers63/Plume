------------------------------------------------------------------------
0. What this note is and is not
------------------------------------------------------------------------
Live plume.py was re-inspected in full before writing this note. Confirmed
already landed: gender agreement (notes_003), the removed "Five natural
alternatives" heading (notes_003). Confirmed NOT yet landed: the finishing
touch picker (notes_004), "Use this" (notes_005), and everything on the
roadmap file (history/favourites, situation box, TTS, quick-swap direction).

This note does not repeat any bug or feature already on file. It proposes:
  1. A small, targeted refactor that reduces the risk of notes_004 and
     notes_005 colliding when both are implemented.
  2. One new feature: a toolbar backend toggle (Claude / Ollama), which
     is the one live-editable Settings field that has no toolbar mirror,
     unlike direction, French form and Me/You gender agreement.

------------------------------------------------------------------------
1. Refactor -- extract a single variation-card builder
------------------------------------------------------------------------
Rationale, grounded in the current code and the two pending notes:

  PlumeApp._render_result (plume.py, from approximately line 1581) builds
  all five alternative cards inline inside one loop: a CTkFrame, two
  CTkLabels (translation, meaning check) and one CTkButton (Copy),
  constructed and grid-placed in sequence.

  Two notes already on file both need to change this exact loop:
    - notes_004 wants each alternative's Copy button to append a chosen
      "finishing touch" to the copied text, and to compose that text
      without altering the stored translation.
    - notes_005 wants to replace the single Copy button with a
      two-button column ("Use this" + "Copy").

  If both are implemented independently against the raw loop, the second
  patch to land will conflict with the first at the exact same lines
  (the button-construction block), and whoever applies them second has
  to manually reconcile two different button layouts. Extracting the
  per-card construction into one method now gives both notes a single,
  named seam to extend, and costs nothing today because the visual
  output is identical to the current code.

  This is refactoring only: no behaviour changes, no new dependencies,
  no widget layout differences. It touches one method and adds one
  private helper.

------------------------------------------------------------------------
2. Feature -- toolbar backend toggle (Claude / Ollama)
------------------------------------------------------------------------
Rationale, grounded in the current code:

  Direction, French form and Me/You gender agreement all live on the
  toolbar (PlumeApp._build_toolbar) and are mirrored into config_data by
  _on_toolbar_change, then carried forward into the saved config by
  SettingsDialog._save's "carry the live toolbar selections forward"
  block (around line 1126). Backend is the one remaining field that
  drives every request but can only be changed by opening Settings,
  which also surfaces the API key and model fields the user is not
  trying to touch when they just want to flip from Claude to Ollama
  mid-session (e.g. to keep a sensitive phrase local).

  This is not on the roadmap file (history, situation box, TTS,
  direction-swap) and is not in notes_001 to notes_005.

------------------------------------------------------------------------
3. User-visible behaviour
------------------------------------------------------------------------
Refactor (1): none. Pixel-identical output; existing tests and manual
behaviour are unaffected.

Feature (2):
  1. The toolbar's top row gains a "Backend" label and a two-value
     segmented button ("anthropic" / "ollama"), to the left of Settings.
  2. Changing it updates the status bar's "Backend: ..." line on the
     next status refresh, exactly as today when Settings is used.
  3. Settings still shows and can change backend (alongside the API key
     and Ollama model fields it already owns). Whichever value the
     toolbar holds at Save time wins, matching the existing rule for
     direction/formality/gender -- so opening Settings and changing only
     the API key, without touching the backend segmented button there,
     cannot accidentally revert a toolbar flip.
  4. No network request is made by toggling. No config keys, prompt, or
     JSON contract changes.

    def normalise_backend(value) -> str:

7. Risks
------------------------------------------------------------------------
  - Column renumbering in _build_toolbar's top row is a pure layout
    change; nothing else keys off those column indices.
  - Edge case (accepted, documented): if a user flips the toolbar
    backend toggle while the Settings window is already open, the
    dialog's own segmented button does not live-update to match. This
    is pre-existing behaviour for any field the toolbar and Settings
    could both expose; the toolbar-wins-at-save rule (5.6) prevents it
    from producing an inconsistent saved file, but the dialog's control
    could briefly look stale while both are open at once. This matches
    the severity and treatment of Finding I in notes_002 (now fixed for
    the other four fields by the same pattern).
  - The refactor in section 1 must land before, or in the same change
    as, whichever of notes_004 / notes_005 is implemented first, or the
    second one to land still has to touch _render_result directly. If
    both are already scheduled for a single implementation pass, the
    refactor can be folded into that pass instead of landing separately.

------------------------------------------------------------------------
8. Deliberately not proposed
------------------------------------------------------------------------
  - History / favourites, situation box, TTS, direction-swap button
    (already on the roadmap).
  - Finishing-touch emotes (notes_004) and "Use this" (notes_005): not
    redesigned here; section 1 only prepares a seam for them.
  - A toolbar control for the Ollama model name or the Claude API key:
    those stay Settings-only, as they are not single-toggle choices.
  - Auto-saving the backend toggle to disk on every click: matches the
    existing "toolbar is session-live, Settings persists" rule used by
    direction/formality/gender.
