2. v1.33 — WHAT THE CURRENT EVIDENCE DOES AND DOES NOT SHOW
==========================================================

build_tone_instruction is at plume.py:1758–1778. The added clause at 1771–1777
preserves negation, quantities, attribution, uncertainty and obligations, and
forbids unexpressed reassurance, gratitude, apologies, availability or agreement.
It distinguishes faithfully translating source slang from inventing more slang.

This is a sensible extension of Plume's existing meaning-preservation contract.
The qualification 'that the source does not express' is important: a faithful
translation must keep an apology, agreement or joke when the source contains it.
The primary risk to test is overcorrection: removing a real social meaning,
flattening source humour, or making natural French/English unnecessarily stiff.
The other risk is undercompliance: Warm/Reassuring/Playful steering the model into
new assertions despite the guard, especially in one of the five alternatives.

Current tests at tests/test_translator_logic.py:530–550 inspect prompt strings.
They establish that the instruction is present and absent as intended, not that
either backend follows it. When no tones are selected, this helper returns an
empty string: the extra guard is not universal across all requests. The broader
translation prompt has its own fidelity rules. Do not silently relocate this
clause into the global prompt during calibration; that would be another change.

Baseline provenance: commit 15542d8 introduced v1.33. The parent version of
build_tone_instruction was inspected directly. Use only that old helper's clause
as baseline, keeping today's validator, request envelope, glossary, writing
profile, model settings and output parser identical. Running the whole old app
would confound the comparison with unrelated changes.

Proposed bounded evaluation
-----------------------------
Use the 24 synthetic source cases below: twelve English and twelve French. Each
has a direction, an assigned tone configuration and a meaning-preservation oracle.
The oracle describes semantic requirements, not one mandatory exact translation.
This makes idiomatic alternatives possible while detecting concrete errors.

Run each case with baseline and candidate once per backend actually intended for
release: 48 responses for one backend, 96 for both. Each response contains the
main translation plus five alternatives, so both backends produce 576 translated
strings to assess. Include the meaning checks and existing validation warnings
in the judgement. Do not declare Ollama calibrated based on Claude outputs.

Four cases have no tones (negative controls), eight use a single tone and twelve
use a compatible triple. No-tone prompt pairs should be identical; variation in
their generated results illustrates sampling noise rather than this clause's
effect. Duplicate no-tone calls may be omitted for cost if prompt equality is
verified, but record that choice in the results.

Keep formality, gender, writing Strength/Role and glossary settings fixed and
record them. Use the user's actual intended model names/versions and the existing
generation settings. A fixed seed/temperature, where supported, helps comparison
but is not a universal determinism guarantee. Disable automatic provider fallback
for the benchmark, otherwise a backend failure can silently confound attribution.
Do not use private conversation history or production credentials in fixtures.

Acceptance and decision rule
------------------------------
1. Run existing structured-result and placeholder/direction checks first.
2. A bilingual reviewer assesses source meaning without seeing which prompt
   produced each output. Randomise A/B labels and record the rubric before scoring.
   Automated/model-assisted review can flag cases but must not be described as
   independent human bilingual sign-off. Substring searches cannot reliably judge
   negation, idioms or politeness across languages.
3. Any invented/removed fact, changed quantity, negation reversal, changed
   obligation, invented commitment or lost source apology is a critical semantic
   failure. Assess all six translations; the main translation alone is insufficient.
4. Acceptance requires zero unresolved critical failures in the candidate sample
   and no systematic loss of naturalness/source tone relative to baseline. Baseline
   failures are not permission to accept the same errors in the candidate.
5. Repeat failures and ambiguous/high-risk cases, preferably three paired runs,
   before assigning cause to the prompt. One favourable model response proves
   neither reliability nor causality. This is a bounded regression evaluation,
   not a statistical demonstration of zero hallucinations.
6. If accepted, record models, date, case data, output/setting hashes, reviewer and
   decisions, and mark calibration complete FOR THOSE configurations. If one
   backend fails, record that backend's result explicitly; do not mark both passed.
7. If a repeatable regression is attributable to the new clause, revise or revert
   ONLY that clause. Keep v1.33's deterministic validator/raw-label fixes. Add the
   failed case to the regression set and rerun after the wording change.

Practical decision now: keep the sensible guard provisionally and keep calibration
honestly labelled pending. No provider generation or human output assessment was
performed in this review, so this note does not close the bilingual calibration.
The absence of endpoint access is a benchmark limitation, not a reason to invent
a new prompt or claim a model-assisted editorial judgement is empirical validation.

Important gap in the existing test claim
----------------------------------------
_http_post_json.wait_or_give_up still calls time.sleep(delay), plume.py:2307.
Checking the Event at 2299 does not wake a sleep already in progress. Up to the
remaining backoff duration can therefore be wasted after cancellation, potentially
up to the available 30-second retry-wait budget for a server-requested pause.

test_cancelled_during_backoff_wait_stops_retry at test_translator_logic.py:1691
sets the Event inside fake_urlopen BEFORE raising HTTPError. It checks cancellation
before the wait starts, not cancellation during a blocked wait. The test is useful
but its name overstates that particular coverage. This is a small responsiveness/
worker-lifetime gap, not evidence that cancelled text reaches the screen.

Smallest recommended source change — PROPOSED ONLY
----------------------------------------------------
In C:\Plume\plume.py, _http_post_json.wait_or_give_up, replace only line 2307's
time.sleep(delay); retain waited += delay at 2308 and the surrounding budget checks:

```python
        if cancel_event is None:
            time.sleep(delay)
        elif cancel_event.wait(delay):
            raise BackendError("The request was cancelled.")
        waited += delay
```

Event.wait(timeout) returns early when the event is set. It preserves the normal
delay for uncancelled requests and the existing no-event API. Python documents
this behaviour explicitly [1]. This is cooperative cancellation during retry
waiting; it does not promise to abort an active HTTP read.

The replacement was applied only to an in-memory copy of the real helper and
tested against a real local HTTP 503 + Retry-After: 2 response. An observed Event
confirmed the wait had actually begun before cancellation was set. The worker
returned cancelled within the measurement rounding (<0.0001 s reported as 0.0000),
with exactly one request. No file containing production code was changed. This
single observation supports the mechanism; it is not a production latency SLA.

Recommended completion criteria
---------------------------------
- Preserve current immediate UI invalidation, request IDs and the Event chain.
- Implement the small wait change and add a genuinely mid-wait test. Coordinate
  with barriers/events; do not rely on a guessed sleep to decide when to cancel.
- Commit a local HTTP integration fixture in tests once implementation is
  authorised. Cover delayed headers, partial body, timeout, retry wait, newer
  request succeeding while an older one is stalled, Clear and close.
- Use real provider wrappers with URLs redirected IN TEST MEMORY to provider-
  shaped local responses, without editing plume_config.json or invoking fallback
  against a real provider. Check request counts and suppressed fallback as well
  as the returned exception. Inspect both success and failure after cancellation.
- Add one GUI integration run: click Clear while the loopback response is held,
  start a second request, release the old response and confirm it cannot replace
  the newer result; repeat closing the window. Use queued barriers/status to know
  the request is genuinely in progress. The four transport checks above do not
  claim this full interaction has already occurred.
- Confirm an uncancelled delayed request still succeeds, cancellation during wait
  wakes promptly (e.g. a generous one-second test bound), and there is exactly
  one server request after cancelling the first attempt.
- On passage, close the item as 'cooperative cancellation verified against
  controlled real HTTP delays; blocked reads remain limited by socket behaviour'.
  Retain the honest limitation in user/developer documentation.

No live Claude/Ollama outage is necessary to establish the client contract.
A live-provider smoke test later is useful for provider-specific behaviour but
should not be the only repeatable validation path. Python's HTTP server supports
the local fixture and urllib exposes a timeout for blocking operations [2,3].

Important limits and future work
---------------------------------
Socket timeouts are not strict whole-request deadlines: a server sending a small
amount periodically may keep a read alive. Clearing repeatedly can leave multiple
abandoned daemon workers waiting on sockets. If observed in normal use, bounded
worker admission or a separate process with a hard deadline would be distinct
requirements, not an unadvertised extension of this cooperative-cancel feature.
Do not promise that local cancellation stops remote inference or billing.

The fallback guard currently recognises cancellation via exception text at
run_backend:2555 onward. Checking the snapshot Event too would make the intent
more explicit, especially when the final failed attempt reports another error.
Both wrappers already pass the same Event into _http_post_json, whose pre-attempt
check prevents a cancelled fallback from sending a POST. A typed cancellation
exception is optional future clean-up, not required architectural churn here.
