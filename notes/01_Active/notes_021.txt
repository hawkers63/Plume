The application would significantly benefit from the introduction of a section that allows users to save their preferred spellings of words. This feature is particularly pertinent in contexts such as online gaming, where users often refer to in-game locations using unique spellings that they would like to see reflected in generated sentences. For instance, when mentioning Auridon in French, users might prefer 'd'Auridia' instead of the default 'Auridon'. A dedicated section for such preferences would enable Claude to utilise these entries, overriding the default settings and thereby applying the user's preferred terminology when constructing sentences. 

Currently, Plume is already well-positioned to support this concept. Within the existing codebase, a feature exists in its nascent form as a translation_glossary, which is a saved list of preferred source and translation pairs that is incorporated into the prompt prior to Claude or Ollama generating the output. 

It is crucial to note that the Auridia example should not be treated as a “keep this word unchanged” directive; rather, it represents a preferred translation rule. Consequently, it belongs in the glossary rather than being classified under “Keep as-is.” For this example, the base terms should be stored as follows:

- Auridon = Auridia
- Auridia = Auridon

It is important not to store only Auridon = d'Auridia, as 'd'' serves as grammatical context rather than the location name itself. Claude should be informed that the preferred French name is Auridia, allowing for natural adaptation in context:

- guardians of Auridon
- les gardiens d'Auridia

This approach aligns with Plume’s current glossary prompt, which indicates that preferred renderings can be adapted grammatically rather than enforced verbatim.

### Prompt Behaviour
The existing prompt clause is on the right track; however, I would recommend enhancing it slightly for this specific use case. The instruction should essentially convey:

Preferred translations: when the source contains one of these terms, utilise the corresponding preferred rendering for the target language. Maintain case and grammar naturally. Apply French contractions and elisions where necessary; for example, 'de + Auridia' may become 'd'Auridia'. These entries should dictate word choice only and must not alter the source meaning, direction, tone, JSON format, or the number of alternatives.

This final clause is crucial. It is imperative that Claude adheres to the preferred term without allowing the glossary to become a covert instruction channel.

### Direction Handling
There are two feasible approaches for handling directionality. The current simplistic method involves maintaining straightforward bidirectional pairs:

- Auridon = Auridia
- Auridia = Auridon

This approach is user-friendly and aligns with the existing code. Alternatively, a more explicit version could incorporate a direction field:

```json
}
```
and:
```json

```

I would recommend not pursuing this complexity unless the glossary expands significantly. For the time being, the two-line approach remains simpler and consistent with Plume’s existing flat configuration style.

### Important Edge Cases
Several small considerations should be deliberately addressed:
- Match terms case-insensitively during validation and de-duplication, while preserving the user’s saved spelling.
- Avoid masking glossary terms with placeholder protection; masking is reserved for terms that must not be translated, whereas glossary terms are intended for controlled translation.
- Deliver the glossary as background context rather than visible output.
- Limit entries, as Plume currently does, to prevent the prompt from becoming unwieldy.
- Allow Claude to adapt grammar: Auridia, d'Auridia, à Auridia, en Auridia, depending on the context of the sentence.
- Maintain the dominance of the source meaning. Should a user input a different location, the glossary should not fabricate Auridia.
