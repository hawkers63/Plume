1. Executive summary
------------------------------------------------------------------------
Plume is a single well-sectioned CustomTkinter module. The deterministic
core (config atomicity, placeholder protection, prompt builder, strict
JSON contract, urllib backends, stale-id helper) is sound and covered
by tests. HTTP is stdlib urllib only; there is no Anthropic SDK and no
requests/httpx. User-facing strings in plume.py are British English.

The remaining defects cluster in the translation lifecycle and Tk
threading, not in the parser:

  - Clear and window-close do not invalidate in-flight work, despite
    project.txt requiring that.
  - Ctrl+Enter is bound with bind_all and does not honour the disabled
    Translate button, so a second request can fire while one is in flight.
  - Settings -> Detect can leave the button stuck on "..." if /api/tags
    returns a non-object JSON body.
  - The status bar never shows "translating..." because format_status
    always overwrites state with the character count.

None of the remaining bugs leak the submitted phrase into diagnostics.
The live Anthropic key is on disk locally, gitignored, and not in git
history.

2. Architecture (current)
------------------------------------------------------------------------
Single module plume.py, eight sections:

  1  Constants, config_dir() / config_path()
     (source: beside the module; frozen: %LOCALAPPDATA%\Plume)
  2  DEFAULT_CONFIG, load_config(), atomic save_config()
     (tmp -> fsync -> os.replace)
  3  Placeholder protect/restore, uniqueness normalisation, source-size
     check
  4  build_translation_prompt(), build_user_envelope(),
     parse_translation_result()
  5  _http_post_json(), call_anthropic(), call_ollama(),
     list_ollama_models(), run_backend(), translate()
  -  Status helpers: format_status(), format_language_label(),
     mask_api_key(), result_is_stale()
  6  SettingsDialog (backend, key, models, Detect, formality, privacy)
  7  PlumeApp dual-pane UI and callbacks
  8  main()

Translation flow:
  1. User types in the left CTkTextbox and presses Translate or Ctrl+Enter.
  2. _translate validates length, copies a config snapshot (direction +
     formality from the toolbar), optionally shows the Claude privacy
     notice, increments _request_id, disables the button, starts a
     daemon thread.
  3. Worker calls translate(snapshot, text): mask placeholders -> build
     prompt/envelope -> run_backend (anthropic -> Claude Messages;
     ollama -> http://localhost:11434/api/chat) -> parse_translation_result
     -> restore tokens.
  4. Worker schedules self.after(0, lambda: self._deliver(rid, text, payload)).
  5. _deliver drops the result if result_is_stale(rid, self._request_id);
     otherwise it renders one main card plus five alternative cards with
     Copy buttons. If the input changed, it keeps the result and shows
     "Generated for an earlier message".

GUI imports are defensive so tests\test_translator_logic.py can import
plume headless.

FINDING A - Clear does not invalidate an in-flight request
  Severity : High
  File     : plume.py, PlumeApp._clear ~1218; _deliver comment ~1306
             claims Clear is handled.

  project.txt requires: ignore a result if a later request, Clear, or
  window close superseded it. _request_id is only incremented in
  _translate (1284). _clear empties the input and results but leaves
  the current id unchanged, so the worker's result is not stale.
  _deliver then renders it and, because the input no longer matches
  snap_text, appends "Generated for an earlier message" -- the cleared
  pane is repopulated.

  Current code (~1218):
        def _clear(self):
            self.input_box.delete("1.0", "end")
            self._clear_results()
            self._on_input_change()

  Recommended fix: insert at the start of _clear:

        def _clear(self):
            """Clear the input and drop any in-flight translation."""
            self._request_id += 1
            self.translate_btn.configure(state="normal", text="Translate")
            self.input_box.delete("1.0", "end")
            self._clear_results()
            self._on_input_change()
            self._refresh_status(state="ready")

FINDING B - Window close during translation can raise TclError
  Severity : High
  File     : plume.py, PlumeApp.__init__ ~1031; worker ~1301;
             _deliver ~1305.

  No protocol("WM_DELETE_WINDOW", ...). Spec: "Close during a request
  produces no Tk callback exception." The worker always does:

                self.after(0, lambda: self._deliver(rid, text, payload))

  If the root is destroyed, after or _deliver (translate_btn.configure,
  etc.) raises TclError. The worker's except Exception does not cover
  the after call (it is outside the inner try) nor the callback body.

  Recommended fix: after _bind_shortcuts() in __init__, and new methods
  on PlumeApp:

            self.protocol("WM_DELETE_WINDOW", self._on_close)

        def _on_close(self):
            """Invalidate in-flight work, then destroy the window."""
            self._request_id += 1
            self.destroy()

        def _deliver(self, rid, snap_text, payload):
            try:
                if not self.winfo_exists():
                    return
            except tk.TclError:
                return
            if result_is_stale(rid, self._request_id):
                return
            # ...existing body...

  And wrap the worker's schedule (replace the bare self.after at 1301):

                def _deliver_safe():
                    try:
                        self._deliver(rid, text, payload)
                    except tk.TclError:
                        return
                try:
                    self.after(0, _deliver_safe)
                except tk.TclError:
                    return

FINDING D - Settings Detect can hang if Ollama's model list is not a
            JSON object
  Severity : High (new)
  File     : plume.py, list_ollama_models 759-777;
             SettingsDialog._detect_models 980-992.

  Current code (~772):
    names = []
    for model in data.get("models", []):

  If /api/tags returns a JSON list or scalar, data.get raises
  AttributeError. That is not wrapped as BackendError. The Detect
  worker only catches BackendError, so _finish_detect never runs and
  the button stays disabled with text "...".

  Recommended fix: in list_ollama_models, immediately after a successful
  json.loads:

    if not isinstance(data, dict):
        raise BackendError("Ollama returned a model list that could not be read.")

  And in _detect_models.worker, catch unexpected failures so the button
  recovers:

            def worker():
                try:
                    names = list_ollama_models()
                    msg = "Found: " + ", ".join(names) if names else "No local models found."
                except BackendError as exc:
                    names, msg = [], str(exc)
                except Exception:
                    names, msg = [], "Could not read the Ollama model list."
                def _finish():
                    try:
                        self._finish_detect(names, msg)
                    except tk.TclError:
                        return
                try:
                    self.after(0, _finish)
                except tk.TclError:
                    return

  The TclError guards also cover closing Settings while Detect is in
  flight (same family as Finding B).

FINDING J - load_config does not coerce types; Translate can throw on
            the Tk thread
  Severity : Medium (new)
  File     : plume.py, load_config 197-199; _translate 1256;
             run_backend 780-785.

  Unknown keys are ignored (good), but values are copied raw. Then:

            limit = int(self.config_data.get("max_input_chars", DEFAULT_MAX_INPUT_CHARS))

  A non-numeric max_input_chars raises ValueError/TypeError on the UI
  thread (no worker yet). A misspelt backend such as "Ollama" is not
  equal to "ollama", so run_backend calls Claude while the user may
  believe they are local. format_status uses the same == "ollama" test,
  so the status bar would also claim Anthropic -- the privacy text would
  be correct, but the surprise send is still wrong if they intended
  Ollama.

  Recommended fix: after the merge loop in load_config:

    backend = str(config.get("backend") or "anthropic").strip().lower()
    config["backend"] = "ollama" if backend == "ollama" else "anthropic"
    try:
        config["max_input_chars"] = int(config.get("max_input_chars"))
        if config["max_input_chars"] < 1:
            raise ValueError
    except (TypeError, ValueError):
        config["max_input_chars"] = DEFAULT_MAX_INPUT_CHARS
    config["privacy_ack"] = bool(config.get("privacy_ack"))
    config["protect_placeholders"] = bool(config.get("protect_placeholders"))

  And in _translate, keep int(...) but it will now be safe.
